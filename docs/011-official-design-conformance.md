# 011 对齐官方设计：一致性审查与路线修正

> 依据：DeepSeek Harness 团队《Super-agent 设计探索：迈向更自主的 Agent 系统》（下称"文章"）。
> 本文记录：官方设计的硬约束、本项目实现与之一致/偏离之处、以及据此**推翻**的决定与新的路线。

## 1. 官方设计的骨架（用于审查的判据）

四个特征：**连续 / 高效 / 主动 / 持久**。五个模块：

| 模块 | 官方要求（判据） |
|---|---|
| §2 双层架构 | Router **不执行具体任务**，只做人类交互与分派，甚至可不配 Bash；Worker 上下文隔离、**不直接对用户说话**，向 Router 汇报 |
| §3 事件驱动 | Trigger 驱动；§3.1 程序层 Fast Path + 语义层 Slow Path 两级过滤；§3.2 订阅**直通**（已归属事件不经 Router）；§3.3 Inline & Spill + 链式召回；§3.4 投机执行 |
| §4 面向人的交互 | §4.1 全双工：耗时工具调用异步返回 Started，不阻塞新输入；§4.2 输出按信道带宽定制（IM 短、GitHub 结构化） |
| §5 计算/状态/环境分离 | Agent Loop 无状态可弹性伸缩，状态入 DB；执行环境留在原地，端侧只放轻量 daemon（BYOM） |
| §6 Watchdog | 主系统**之外**的独立 Control Loop，定时消息驱动；不只探活，还要判断 Worker 有无实质进展/是否偏离，并能在自然语言下修正系统行为 |
| §8.3 上下文边界 | **需要共享上下文的范围共用一个实例，需要隔离的范围各自独立配备**——实例边界 = 上下文边界 |

## 2. 一致性审查（当前适配版）

| 项目 | 状态 | 说明 |
|---|---|---|
| Router 不干活 | ✅ 一致 | 主 Session 工具被限制为 shell/read/jobs（`MASTER_TOOLS`，无 write/edit） |
| Worker 不直接对外 | ✅ 一致 | 执行器 Session 只在工单内工作，回复经 Router 与 Source 投递 |
| 两级过滤 | ✅ 一致 | `src/admission.ts`（程序层准入表）+ assessment（语义层） |
| 订阅直通 | ✅ 一致 | Thread 订阅与直投，另有 `POST threads/:key/unsubscribe` |
| 投机执行 | ✅ 一致 | "静默复现并修复"策略形态 |
| 全双工（异步 ReAct） | ⚠️ 依赖 DSH | 文章称已在 DSH 实现但未默认开启；本项目未确认开启状态 |
| Inline & Spill | ⚠️ 在 DSH 层 | `spill-local` / `spill-policy`（`maxInlineTokens`）由 profile 提供，插件不感知 |
| 链式召回 | ⚠️ 部分 | 对象有稳定 ID（Trigger/Thread/Session），但"每次召回内联下一跳 ID"的闭环未在本适配版 验证 |
| 存算分离 | ❌ 未实现 | 原型与当时的桌面外壳都是"单机跑"，状态在本地 sqlite；这是原型的简化，不是本项目的偏离 |
| **Watchdog** | ❌ **缺失** | 全仓库 grep 零命中；本项目只有文档里的"每小时巡检"（只查退出码，不判断进展），弱一档 |
| **实例 = 上下文边界** | ❌ **曾被本项目违反** | 前两轮把"一个进程服务 N 个仓库"当主路线，与 §8.3 相反 |

## 3. 据此推翻的决定

### 3.1 推翻：单进程多仓库（原 C2/C3 主路线）

**理由**：§8.3 把扩展方向定为"按上下文边界划分实例"。一个进程装多个仓库会：

- 让不同边界共享同一份 Router 全局记忆（§2.1 的"全局序点与记忆"会被污染）
- 共享同一套策略与凭据边界（§8.4 的安全前提被削弱）
- 迫使所有 Source 级状态（游标、Thread、重试表）都要按实例切分——这正是上一轮反复踩坑的地方

**改法**：

1. 恢复"**一个进程一个上下文边界**"的守卫：配置多个 GitHub Source 时给出明确 setup 问题，指引"按边界多起实例"（`docs/010` 的 C2/C3 从主路线降级为**未采纳方向**）
2. 多上下文的正解是**多实例**：多个 DSH profile / 多个应用实例，各自独立状态、独立重启、独立 Watchdog
3. 已写的逐实例管线**不删**（`deployments`/`problemFor`/`ctx.source`/状态命名空间）：它对"多实例管理"与将来"同上下文多仓库"仍有价值，且当前被守卫挡住、无行为变化

### 3.2 修正：把投入转向官方五模块中真正缺失的部分

按价值排序：

1. **Watchdog（§6）** —— 唯一完全缺失的模块；对"持久在线"贡献最大，且与多仓库无关
2. **全双工（§4.1）** —— 先确认 DSH 的异步工具调用在 superagent preset 中是否开启，未开则开启；这是"高效"的直接来源
3. **链式召回（§3.3）** —— 验证 Trigger→Thread→Session→另一 Thread 的按需展开是否闭环，补齐缺失的内联 ID
4. 存算分离（§5）保持"原型简化"状态，不作承诺

### 3.3 保持不变

- Windows 平台适配：与文章设计正交，继续维护；应用外壳已于 2026-11-07 移除，不再维护
- 声明式配置（`docs/009`）：配置即代码，对多实例管理尤其有用（每个实例一份配置）
- 测试与契约：所有改动继续以"测试全绿 + 真实服务可用"为门槛

## 4. 多实例形态（作为 §8.3 的实现方向）

| 维度 | 单实例（现状） | 多实例（目标） |
|---|---|---|
| 上下文边界 | 一个仓库 | 每实例一个仓库/一个团队 |
| 状态 | `<stateDir>` | 每实例独立 `<stateDir>` |
| 配置 | 一份 `superagent.settings.json` | 每实例一份（声明式配置天然支持） |
| 生命周期 | 一个进程 | 独立启停、独立升级 |
| Watchdog | 无 | **每实例一个外部 Control Loop** |

这条路线也解释了为什么多实例比多仓库更省事：隔离靠进程/状态目录天然实现，不需要在每个子系统里做实例切分。

## 5. 结论

前两轮的 C2/C3 是对官方设计的一处**方向性误判**：它们把"扩展"理解成"单实例承载更多仓库"，而官方要求的是"按上下文边界增加实例"。本文记录该修正，后续工作按 §3.2 的优先级推进。
